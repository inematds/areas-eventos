MÓDULO 2.1

Claude → Codex: separe o cérebro do modelo

Explicar por que o lock-in mora no runtime e como o método Auditar → Adaptar → Provar → Handoff leva o conhecimento do projeto para um núcleo portátil.

0% 0 de 0

O que é

A área Claude → Codex parte de uma frase: "Não migre o seu cérebro. Separe o cérebro do modelo." O "cérebro" é tudo o que você acumulou num projeto: contexto, regras, decisões, tarefas, skills, handoffs e memória. Segundo a página, só CLAUDE.md e AGENTS.md estão presos ao provedor; todo o resto é Markdown portátil, texto simples que qualquer agente consegue ler. Quando esse material vive numa camada portátil dentro do projeto, Claude Code, Codex CLI, Gemini ou um modelo local em container viram apenas executores, isto é, programas que fazem o trabalho a partir desses arquivos. Trocar de modelo passa a ser trocar uma borda, não o centro. A área junta a tese, o método, um curso de 3 trilhas, um kit de scripts e mega-prompts que fazem isso na prática.

Por que aprender

Modelos mudam com frequência, por preço, acesso ou qualidade. Se o conhecimento do projeto estiver no lugar certo, cada troca custa pouco em vez de exigir reconstrução.

Conceitos-chave

cérebro = contexto, regras, decisões, tarefas, skills, handoffs e memória; Markdown portátil; executor; trocar a borda, não o centro

O que é

Lock-in é ficar preso a um fornecedor porque sair dele custa caro. A página afirma: "O lock-in não está no modelo. Está no que você deixou dentro do runtime." Runtime é o programa que roda o agente, como o Claude Code ou o Codex CLI. Quem usa um assistente de código há alguns meses acumulou instruções, memória, skills, hooks e milhares de sessões num formato que só aquele runtime lê. A página descreve três mudanças: o lock-in é invisível até o dia da troca; o mesmo conhecimento pode servir a qualquer modelo; e você passa a ter menos dependência e mais controle. O conteúdo é durável, o formato é descartável, e misturar os dois é o que trava a migração.

Por que aprender

A área é para quem usa Claude Code ou Codex em projetos reais e teme a troca de modelo. Entender onde está a dependência mostra o que precisa sair do runtime antes que a troca seja obrigatória.

Conceitos-chave

lock-in; runtime; CLAUDE.md, memória nativa e sessões JSONL são armazenamento do trabalho, não o trabalho; conteúdo durável, formato descartável

O que é

O método tem quatro passos, nessa ordem: Auditar, Adaptar, Provar e Handoff, "nunca implementando antes de auditar". Auditar é fazer um inventário somente leitura dos dois runtimes: skills, comandos, subagentes, hooks e MCP; cada skill vira reutilizável, adaptador, nativo ou não resolvido. Adaptar é dividir o CLAUDE.md: regras portáteis vão para o AGENTS.md, e o que depende de plugin, hook ou menu do Claude fica no arquivo específico, que apenas importa o portátil. Provar é abrir uma sessão nova e fazer cinco perguntas de continuidade: objetivo e critério de pronto, uma regra com o arquivo de origem, a última decisão, a próxima ação e conflitos. Handoff é gravar decisões, pendências, próximos passos e caminhos num Markdown que a próxima sessão lê antes de agir.

Por que aprender

A ordem evita o erro mais caro: mudar arquivos antes de saber o que existe. E a regra de prova impede que você confunda arquivo criado com conhecimento realmente usado.

Conceitos-chave

Auditar → Adaptar → Provar → Handoff; MODE: audit; portátil × resíduo; cinco perguntas de continuidade; arquivo existir não é prova

O que é

O núcleo portátil são sete lugares, cada um com um dono e uma regra de atualização. AGENTS.md guarda regras estáveis e ordem de leitura; context/overview.md, fatos verificados com fonte e data; context/current-state.md, o que funciona e o que está pendente; context/sources.md, de onde vem cada informação. context/decisions/ tem uma decisão aceita por arquivo; tasks/current.md traz objetivo, dono, critério de pronto e próxima ação; handoffs/latest.md é a continuação para a próxima sessão. A página avisa que esses nomes são convenção: nenhum runtime carrega essas pastas sozinho, quem manda ler é a ordem de leitura no topo do AGENTS.md. Cada informação tem um tipo: fato, preferência, hipótese ou decisão, e "provenance vence timestamp", ou seja, a origem pesa mais que a data e nada se apaga, usa-se superseded_by.

Por que aprender

Misturar fato com hipótese, ou decisão com preferência, faz o agente repetir erro antigo e contradizer o que já foi resolvido. Dono e data permitem promover uma informação para contexto aprovado, sempre com a sua aprovação.

Conceitos-chave

AGENTS.md; context/; decisions/; tasks/current.md; handoffs/latest.md; fato, preferência, hipótese, decisão; provenance vence timestamp; segredos fora do repositório

O que é

A página separa a decisão em três níveis de esforço, não em opiniões. Nível 1 é importar no app, com um clique: rápido, mas limitado ao que o outro lado aceita, e o CLI do Codex, por exemplo, não tem import nativo. Nível 2 é migrar com o kit, com um comando: rodar os scripts do agente-claude-codex para auditar, adaptar, instalar o núcleo, portar skills e provar. Nível 3 é a camada pessoal portátil, duradoura: o conhecimento vive no projeto e o runtime fica intercambiável. Ficar agnóstico, isto é, não depender de nenhum modelo específico, é o nível 3, e segundo a página é o único que sobrevive à próxima troca. Agnóstico não é abandonar o Claude: você continua escolhendo o executor por tarefa.

Por que aprender

Nem todo mundo precisa do nível 3 agora. A página lista quando migrar já, por custo, acesso ou política, e quando vale ficar agnóstico, como ao usar dois executores ou ter trabalho de cliente.

Conceitos-chave

Nível 1 importar; Nível 2 migrar com o kit; Nível 3 camada pessoal portátil; migrar agora × ficar agnóstico; custo de não fazer nada

O que é

O curso Claude → Codex: migre ou fique agnóstico é aberto, em português, com versões em inglês e espanhol; segundo o currículo, são 3 trilhas, 18 módulos e 108 tópicos. A Trilha 1 cobre fundamentos e vocabulário, a Trilha 2 é o kit comando por comando e a Trilha 3 traz seis projetos sobre um sistema real. O kit agente-claude-codex é bash mais Markdown, em três formas de uso: scripts, mega-prompts e o template do núcleo portátil. O doctor.sh responde "meu ambiente está pronto?" e o audit.sh grava um relatório somente leitura; há ainda adapt-instructions.sh, init-core.sh, sync-skills.sh com polyskill, readback-test.sh, drift-report.sh e promover-memoria.sh. A página resume: "O melhor primeiro passo é um projeto seu, em modo audit."

Por que aprender

O curso explica o porquê e o kit faz o trabalho sem apagar nada: nada em ~/.claude ou ~/.codex é copiado em massa ou apagado, e instalar skill faz backup ao lado. Começar pela auditoria mostra em uma sessão o que é portátil e o que depende de hook.

Conceitos-chave

curso de 3 trilhas; kit agente-claude-codex; doctor.sh; audit.sh; mega-prompts A e B; Mapa do tema; área irmã Codex + Claude

MÓDULO 2.2

Codex + Claude: um faz, o outro confere

Explicar como usar Claude e Codex no mesmo projeto, com os seis níveis do kit Use Both, o cartão de rotas e a diferença entre claudex e Use Both.

0% 0 de 0

O que é

A área Codex + Claude tem como tese: "Um planeja, o outro critica. Use os dois juntos." A ideia é que Claude e Codex se completam quando cada um faz uma parte e o outro confere o artefato real, isto é, o arquivo, o diff ou a imagem de verdade. A regra que atravessa tudo: o segundo assistente recebe o mesmo briefing e o artefato real, nunca um resumo vago do que o primeiro fez. A página é o ponto de encontro do INEMA sobre as duas ferramentas e reúne os seis níveis do kit Use Both, a tabela de quem faz o quê e os cards de todos os cursos e projetos. Para migrar de um para o outro, o caminho continua sendo a área irmã Claude → Codex.

Por que aprender

É para quem já tem Claude Code e Codex e não quer escolher um só. Um segundo olhar, de outro modelo, pega falhas que o autor tende a deixar passar.

Conceitos-chave

um faz, o outro confere; artefato real; mesmo briefing; não é Claude ou Codex; área irmã Claude → Codex

O que é

O kit Use Both organiza o uso conjunto em seis níveis de fluxo de trabalho, com prompts prontos e duas skills pequenas. Nível 1 é deixar as duas discutirem: uma escreve o plano, a outra critica o mesmo arquivo, só lendo, em no máximo duas rodadas. Nível 2, opcional, é gerar imagens, só se houver ferramenta de imagem na sessão e depois de conferir acesso e cobrança. Nível 3 é dividir construir e revisar: uma constrói num branch, a outra revisa o diff com o briefing e o resultado dos testes. Nível 4 é o uso supervisionado do computador, com senha, pagamento e envios importantes sob o seu controle; nível 5 é uma meta com condição de parada, com sucesso observável e limites de arquivos, rodadas e gasto. Nível 6 é handoff e prime: o handoff grava o estado num arquivo portátil e o prime faz o próximo assistente ler e verificar esse estado antes de continuar.

Por que aprender

Os níveis dão uma escada: dá para começar pela discussão de um plano e subir só quando precisar. Cada nível já traz o limite que evita gasto ou ação sem controle.

Conceitos-chave

discutir; gerar imagens; construir e revisar; uso supervisionado do computador; meta com condição de parada; handoff e prime

O que é

O cartão de rotas é uma tabela do kit que diz, para cada tarefa, quem faz a primeira passada, quem faz a segunda e qual é a linha de chegada. Planejar o trabalho: Claude / Opus planeja, o Codex critica as premissas, e o resultado é um plano com escopo e testes de aceite. Construir uma feature: Claude / Opus constrói, o Codex revisa o diff, e o pronto é testes passando e achados resolvidos. Atacar um bug difícil: Codex com uma meta delimitada, testes e um checkpoint humano. Trocar de sessão ou de modelo: snapshot de handoff, e o prime confere o estado atual. A página avisa que são "escolhas editoriais, não ranking medido de modelos": experimente e fique com a rota que produzir melhor evidência.

Por que aprender

Ter uma rota inicial evita discutir do zero a cada tarefa. Saber que ela não é benchmark evita tratá-la como verdade fixa.

Conceitos-chave

primeira passada; segunda passada; linha de chegada; escolhas editoriais, não ranking; modelos e cobrança mudam conforme a conta

O que é

A página organiza cursos e projetos num caminho: entender, migrar ou ficar agnóstico, usar os dois juntos e automatizar o debate. O elo comum são os arquivos Markdown do projeto, como AGENTS.md, tasks e handoffs, que qualquer runtime lê. Nesse caminho aparecem duas ferramentas diferentes. O claudex é um plugin do Claude Code, ou seja, software: o Claude escreve o PLAN.md e o Codex critica de 3 ângulos, em loop até LGTM ou N rodadas. O Use Both é um kit de método, com guia, prompts, templates e 2 skills, cobrindo os seis fluxos, de forma manual ou semiautomática. A página resume: são complementares; plano grande, claudex; o resto, como revisar diff, meta com condição de parada e trocar de sessão, Use Both.

Por que aprender

Saber em que camada cada ferramenta atua evita instalar software para um problema de método, ou o contrário.

Conceitos-chave

Entender → Migrar → Usar os dois → Automatizar o debate; claudex = software; Use Both = método; LGTM; complementares

O que é

A página traz um caso real: quem tem assinatura do Codex e usa o gerador de imagem dele, o image_gen, que no INEMA é chamado de "imagem 2.5". Hoje, no INEMA, o Claude Code chama codex exec em modo não interativo e pede ao image_gen um PNG numa pasta; se o Codex falhar ou não houver crédito, cai para o modelo local FLUX.2 klein. Cada geração consome crédito da assinatura, por isso roda só quando autorizada, e a imagem é conferida depois, porque o texto das bordas pode vir inventado. O kit propõe o nível 2 peça a peça: confirmar antes a ferramenta e a cobrança, nunca trocar sozinho para uma API paga, salvar o arquivo real no projeto e abrir no tamanho de uso. A diferença, nas palavras da página: o do INEMA é em lote e automático, com fallback local; o do kit é manual, com mais checagem de custo e de revisão.

Por que aprender

Imagem gerada tem custo e erros visíveis. As duas abordagens mostram como equilibrar automação com conferência antes de usar o arquivo.

Conceitos-chave

image_gen; codex exec; fallback FLUX.2 klein; checar antes, inspecionar depois; versões irmãs em vez de sobrescrever

O que é

A página resume o começo assim: "O melhor primeiro passo: um plano seu, revisado pelo outro." Escolha uma tarefa pequena, escreva o briefing e o critério de aceite, peça o plano a um e a crítica ao outro, sobre o mesmo arquivo, no máximo duas rodadas, e faça handoff antes de fechar a sessão. A área reúne seis cursos: Claude → Codex (PT, EN e ES), Codex Básico, Master Codex, iClaudeX, MakeClaudeX e DeepClaudeX. Também reúne kits e referências: agente-claude-codex, Use Both, claudex no GitHub, Codex Cheat Sheet e o Mapa do tema no INEMA.CLUB. A página cita um vídeo externo de Mark Kashef, que o kit Use Both acompanha, como fonte de opiniões do autor, sem benchmark; o resumo dele fica no RESUMO-VIDEO.md do repositório do kit.

Por que aprender

Um primeiro ciclo curto mostra na prática o valor do segundo olhar. Os cursos e kits deixam claro onde aprofundar cada etapa.

Conceitos-chave

um plano seu, revisado pelo outro; no máximo duas rodadas; Codex Básico; Master Codex; iClaudeX; MakeClaudeX; DeepClaudeX; Use Both; claudex; Codex Cheat Sheet

MÓDULO 2.3

OSWork: qual edição é pra você

Explicar o que é o OSWork, o que se constrói nele e qual das cinco edições (v2, v6.2, v6, v5, Quick) combina com a experiência e o tempo de cada pessoa.

0% 0 de 0

O que é

O OSWork se apresenta como "IA como sistema de trabalho" e "do chat ao seu ambiente de agentes". Um agente é uma IA que executa tarefas com ferramentas e arquivos, e não só responde numa conversa. O curso ensina a organizar arquivos, instruções, memória e ferramentas em um sistema de trabalho que você consegue verificar. A frase central da página é: "Sua próxima conversa pode começar de onde a anterior parou." Para isso, o OSWork ensina a transformar pedidos soltos em trabalho organizado: definir o objetivo, escolher o contexto, executar uma tarefa pequena e conferir o resultado. Você começa no chat e avança até um bot restrito e a operação supervisionada em uma VPS, um servidor alugado na internet.

Por que aprender

Sem organização, cada conversa com a IA recomeça do zero. Um sistema com arquivos e regras guarda o que já foi decidido e deixa o resultado conferível.

Conceitos-chave

sistema de trabalho; do chat ao ambiente de agentes; objetivo, contexto, tarefa pequena, conferência; bot restrito; VPS supervisionada

O que é

A página oferece "cinco caminhos para organizar seu trabalho com IA" e pede para escolher pela sua experiência e pelo tempo disponível. OSWork v2 é o percurso técnico. OSWork v6.2 é o percurso completo, passo a passo. OSWork v6 é para iniciantes, visual. OSWork v5 é para iniciantes 40+. OSWork Quick é direto ao ponto. Segundo a página, há cursos e vídeos em português, espanhol e inglês; pelo acesso da área, v6.2 e v6 têm links próprios em EN e ES.

Por que aprender

Escolher a edição certa evita desistir no primeiro terminal ou se entediar com o básico. A mesma ideia chega por caminhos de profundidade diferente.

Conceitos-chave

v2 técnico; v6.2 completo passo a passo; v6 iniciantes visual; v5 iniciantes 40+; Quick direto ao ponto

O que é

O OSWork v2 é o percurso técnico: oito módulos, quatro trilhas e 48 tópicos. Vai do chat ao terminal e Codex, arquivos, Skills, Git, bot no Telegram e operação supervisionada em VPS, e inclui kit de prática. Os oito módulos são: Modelos; Chat, Work e Desktop; Terminal e Codex na prática; Pastas, Markdown e segredos; AGENTS, Skills e memória; Git e GitHub sem perder trabalho; Telegram como interface de trabalho; e VPS do zero e operação 24/7. O OSWork v6.2 é esse mesmo percurso refeito para quem está começando: oito módulos e 48 aulas de uns 15 minutos, com passo a passo visual e um glossário dos termos técnicos. No v2, o aluno marca tópicos lidos, registra dúvidas, faz notas e exporta a jornada; o progresso fica no navegador e é separado por idioma.

Por que aprender

Quem quer chegar até bot e servidor precisa do percurso inteiro. O v6.2 permite fazer esse caminho mesmo sem base técnica.

Conceitos-chave

v2: 8 módulos, 4 trilhas, 48 tópicos, kit; v6.2: 48 aulas de ~15 min, glossário; Codex; Skills; Git; Telegram; VPS

O que é

Três edições são para iniciantes e não pedem instalação nem programação. O OSWork v6 tem sete aulas de uns 15 minutos com telas de chat simuladas, antes e depois reais e passo a passo visual; você monta pastas por assunto, uma ficha com as suas regras, um molde de pedido e uma rotina de conferência, sem instalar nada. O OSWork v5 é para profissionais 40+ com pouca familiaridade com IA: sete aulas de 20 a 25 minutos para organizar pastas, orientações, pedidos reutilizáveis e uma rotina de conferência, sem programação. O OSWork Quick é a versão curta e visual para profissionais 40+: sete aulas e cerca de 77 minutos de estudo, com os mesmos assuntos do v5 e menos texto. O Quick também existe em vídeo, com avatar e voz do Nei, ilustrações e legendas SRT, em português, espanhol e inglês.

Por que aprender

Para quem está começando, o ganho vem de organizar e conferir, não de ferramentas técnicas. Essas edições entregam isso em pouco tempo.

Conceitos-chave

v6: 7 aulas de ~15 min, visual, sem instalar; v5: 7 aulas de 20 a 25 min, 40+; Quick: 7 aulas, ~77 min, também em vídeo

O que é

A página lista o que se constrói no percurso: uma pasta de projeto com entradas, saídas e instruções próprias; uma memória de decisões e falhas, junto de uma Skill reutilizável; um histórico Git para revisar e recuperar mudanças; e um bot de consulta com dados fictícios e um plano de operação. Uma Skill é um procedimento empacotado que o agente reaproveita; Git é um sistema que guarda versões dos arquivos. A seção do kit diz: "Seu primeiro ambiente começa com arquivos reais." O kit reúne modelos de AGENTS.md, memória, decisões, registro de falhas, contrato de tarefa, Skill de relatório e plano de VPS, e inclui um bot Python com autoteste offline. O bot de treino é determinístico: não chama um modelo de IA nem executa mensagens como comandos.

Por que aprender

Terminar com arquivos concretos, e não só com anotações, é o que torna o aprendizado reaproveitável no trabalho. Os modelos do kit poupam o começo do zero.

Conceitos-chave

pasta de projeto; memória de decisões e falhas; Skill; Git; bot de consulta com dados fictícios; kit ZIP; bot determinístico

O que é

A página orienta: "Comece com uma tarefa pequena." São três passos: escolher o primeiro módulo e comparar duas opções disponíveis no seu ambiente; criar uma pasta de treino e adaptar o contrato de tarefa do kit; guardar o resultado, registrar uma dúvida e voltar à sua jornada. Na seção "Antes de começar", a página responde que dá para iniciar pelos fundamentos sem programação, e que os laboratórios técnicos apresentam terminal, Git e Python passo a passo. O conteúdo pode ser lido sem cadastro; assinaturas, consumo de API e contratação de VPS são serviços separados, escolhidos pelo aluno. E o curso não promete um agente autônomo sem supervisão: ensina limites, verificação, logs e recuperação.

Por que aprender

Uma tarefa pequena mostra resultado rápido e revela o que falta organizar. Saber o que é pago à parte evita surpresa.

Conceitos-chave

tarefa pequena; pasta de treino; contrato de tarefa; sem programação no início; leitura sem cadastro; serviços pagos à parte; operação supervisionada
